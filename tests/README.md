# Проверки реализации Serpent

Требуются Python 3.9+ и Icarus Verilog с поддержкой SystemVerilog. Python-пакеты
из сторонних источников не нужны. Команды ниже выполняются из корня репозитория.

```sh
python3 tests/run_tests.py --reference-only
python3 tests/run_tests.py
```

Вторая команда запускает два автономных теста со статичным нулевым ключом и
24 конфигурации: обе архитектуры (`1-s`, `2-s`),
три размера ключа (128, 192, 256 бит), одиночный top и ECB с `BLOCKS=1,2,3`.
`--variant 1-s` и `--key-bits 128` ограничивают матрицу для отладки.
`--seed` меняет воспроизводимую псевдослучайную последовательность; по умолчанию
используется `1582251543`. При ошибке сравнения процесс возвращает ненулевой код.

Если исполняемые файлы не доступны через `PATH`, укажите их явно:

```sh
IVERILOG=/absolute/path/to/iverilog VVP=/absolute/path/to/vvp python3 tests/run_tests.py
```

Трассы, скомпилированные симуляции и отчёт `results.json` сохраняются в
`tests/.build/`; каталог исключён из Git. Каждый запуск перезаписывает отчёт
только своей выбранной матрицей. Файл появляется после успешного завершения
всех выбранных конфигураций; при разборе ошибки следует учитывать, что старый
отчёт от предыдущего запуска может ещё находиться в каталоге.

## Откуда берутся правильные ответы

`kat_vectors.json` содержит 27 внешних known-answer tests: по девять тестов
для каждого размера ключа. Они взяты из наборов NESSIE, опубликованных одним
из авторов Serpent, Эли Бихамом:

- [Страница Serpent с пояснением формата](https://biham.cs.technion.ac.il/Reports/Serpent/)
- [128-битный ключ](https://biham.cs.technion.ac.il/Reports/Serpent/Serpent-128-128.verified.test-vectors)
- [192-битный ключ](https://biham.cs.technion.ac.il/Reports/Serpent/Serpent-192-128.verified.test-vectors)
- [256-битный ключ](https://biham.cs.technion.ac.il/Reports/Serpent/Serpent-256-128.verified.test-vectors)

У каждой записи сохранены номер набора и номер вектора; у каждого исходного
файла — URL, дата загрузки и SHA-256 **полного файла источника**. Полные файлы
не включены в репозиторий. Выборка покрывает ненулевые биты в начале/конце
ключа, крайние биты открытого текста, полностью нулевые/единичные значения и
неоднородные байтовые строки из набора 4. Ожидаемые шифртексты не генерируются
из тестируемого RTL.

`reference_serpent.py` — отдельная простая реализация спецификации на Python.
Она сначала проверяется по всем 27 внешним KAT и только после этого служит
эталоном для дополнительных входов. Табличные подстановки выполняются по
отдельным битовым позициям; код предназначен для проверки, а не для защиты
реальных секретов. Его исполнение не является constant-time.

В JSON шестнадцатеричная строка задаёт последовательность байтов в порядке
NESSIE. На RTL-порту первый байт расположен в `[7:0]`. Поэтому, например,
`001122...EEFF` из файла превращается в числовой литерал
`128'hFFEEDDCCBBAA99887766554433221100`. Упаковка использует
`int.from_bytes(value, "little")`; первый ECB-блок занимает младшие 128 бит.

## Что проверяется

- Соответствие KAT для всех трёх размеров ключа; в ECB каждый KAT находится
  в нулевой полосе, а остальные полосы содержат различные дополнительные блоки.
- Точная задержка: принято на фронте `n` — выдано на фронте `n+32` либо `n+16`.
- Поток из 96 входов подряд с интервалом приёма один такт, затем пропуски входов.
- Порядок блоков и отсутствие повторений/потерь вне явно отменённых операций.
- `in_ready`, `key_ready`, `out_valid`, а также нулевой `data_out` при невалидном
  выходе — на каждом проверяемом такте.
- Отказ от приёма до первой загрузки ключа и после сброса.
- Сброс без загрузки ключа при полном конвейере, в том числе на фронте,
  когда ожидался выход; отдельно приоритет сброса над одновременными загрузкой
  ключа и подачей данных.
- Загрузка ключа при полном конвейере, отмена старых блоков, включая результат,
  который без загрузки появился бы на этом же фронте; две загрузки подряд.
- Изменение `key_in` без `key_load` не меняет активный ключ.
- Упаковка нескольких ECB-блоков: различные данные полос обнаруживают их
  перестановку или ошибочное размножение одной полосы.

`tb_pipeline.sv` сравнивает выходы с независимой потактовой моделью протокола,
построенной Python-скриптом. Для входа KAT в нулевой полосе используется
непосредственно опубликованный шифртекст. Остальные ответы считает эталон.

В каждой папке `1-s`/`2-s` также есть автономный `tb_serpent.v`: он проверяет
внешний NESSIE Serpent-256 set 3 vector 0, задержку и пустой такт после выхода.
В нём ключ равен нулю с начала симуляции и не меняется до загрузки; это также
проверяет инициализацию комбинационного расписания ключей при статичном входе.

```sh
cd 1-s
iverilog -g2012 -s tb_serpent_pipelined -o /tmp/serpent-smoke.vvp serpent_*.v tb_serpent.v
vvp /tmp/serpent-smoke.vvp
```

Для второго варианта аналогично используйте каталог `2-s`.

## Ограничения

Это функциональная RTL-симуляция с конечным числом входов. Она не заменяет
формального доказательства, полного покрытия всех ключей и входов, проверки
после FPGA-синтеза и трассировки, либо испытаний реального устройства.
Задержка проверяется в тактах; частота, площадь, энергопотребление и пропускная
способность в бит/с здесь не измеряются. Защита от физических побочных каналов
и навязанных сбоев не заявляется. ECB проверяется как независимое шифрование
упакованных блоков и не является рекомендацией режима для прикладного
шифрования сообщений.
