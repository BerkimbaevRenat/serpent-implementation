# Исправления реализации и уточнения курсовой

Этот документ относится к текущим вариантам `1-s/` и `2-s/`. Исходный `Serpent.pdf` сохранён без изменения: исходный файл вёрстки курсовой не предоставлен. Приведённые ниже пояснения можно использовать при подготовке новой редакции текста.

## 1. Расписание ключей

Для подключа с номером `j`, где `0 <= j <= 32`, нужен S-блок с индексом `(3 - j) mod 8`: последовательность `S3, S2, S1, S0, S7, S6, S5, S4, ...`.

Ранее использовалось `(j + 3) % 8`, дававшее другой порядок. Теперь записано `(35 - j) % 8`: оно эквивалентно нужному индексу и сохраняет неотрицательный аргумент остатка для всего диапазона `j`. Ошибка затрагивала оба варианта и меняла сам результат шифрования.

Также устранена ошибка инициализации в симуляции: процедурный блок `always @*` мог не вычислить расписание для ключа, который был задан нулём с начала симуляции и не менялся. Теперь используется `always_comb`, который выполняется в том числе при старте симуляции. Оба автономных теста проверяют именно такой неизменный нулевой ключ.

Основание: [авторское описание Serpent, раздел 4](https://www.cl.cam.ac.uk/archive/rja14/Papers/serpent.pdf).

## 2. Порты S-блока и ECB

В шаблоне S-блока варианта `2-s` восстановлены входы `x0`, `x1`, `x2`, `x3`. ECB-обёртки получили тактовый и управляющие сигналы, передаваемые каждому ядру. Группа параллельных блоков теперь использует тот же протокол загрузки ключа, сброса и действительности данных, что и одиночное ядро.

## 3. Ключ, сброс и действительность данных

Фиксированный ключ заменён загружаемым. Параметр `KEY_BITS` поддерживает 128, 192 и 256 бит; короткий ключ дополняется единичным битом и затем нулями до 256 бит. Вектор содержит первый байт ключа в младших восьми битах.

На фронте `key_load` сохраняются 33 подключа и отменяются незавершённые блоки. Совместная загрузка ключа и входного блока не допускается: блок на этом фронте игнорируется. После синхронного сброса требуется новая загрузка ключа. Порты `in_valid`, `in_ready`, `out_valid` задают однозначное соответствие входных и выходных блоков; недействительный `data_out` равен нулю. Полный протокол приведён в [README](../README.md).

Загрузка ключа реализована через комбинационное разворачивание расписания и регистры подключей. Для аппаратной реализации нужно отдельно проверить этот путь по времени. Добавленная логика меняет число ресурсов по сравнению с первоначальным проектом.

## 4. Проверка корректности

Печать выходных значений в консоль сама по себе не выявляла ошибку шифрования. Автоматические проверки запускаются командой `python3 tests/run_tests.py` и проверяют соответствие ожидаемым результатам. Конкретный состав проверок и причины отказа задаются файлами в `tests/`.

Сравнение двух архитектур полезно, но недостаточно: обе могли содержать одну ошибку в общих компонентах. Необходимо сравнение с независимым эталоном и известными тестовыми векторами с одинаковым порядком байтов. Проверка модели не заменяет синтез и анализ аппаратных временных ограничений. Этот документ не фиксирует число прошедших тестов: результат относится к конкретному запуску и версии исходников.

## 5. Пропускная способность и задержка

Задержка блока и интервал между принимаемыми блоками — разные величины. Для обеих архитектур интервал `II` равен одному такту; при непрерывном потоке и заполненном конвейере:

```text
Пропускная способность одного ядра = 128 * f / II бит/с
Задержка отдельного блока = L / f секунд
```

Здесь `f` — достигнутая тактовая частота, `L = 32` для `1-s` и `L = 16` для `2-s`. Делить потоковую пропускную способность на число ступеней конвейера нельзя. Паузы, загрузка ключа и сброс снижают среднюю полезную скорость конкретного сеанса.

Если **условно подставить частоты из прежней таблицы**, арифметический пересчёт даёт:

| Вариант | Прежняя частота, МГц | `L`, тактов | `128 * f`, Гбит/с | `L / f`, нс |
| --- | ---: | ---: | ---: | ---: |
| `1-s` | 232,88 | 32 | 29,80864 | 137,4098 |
| `2-s` | 143,93 | 16 | 18,42304 | 111,1651 |

Это **пересчёт старых чисел, а не измерение исправленного проекта**. При этих частотах у `1-s` выше потоковая пропускная способность, а у `2-s` меньше задержка отдельного блока. Новые частоты и количество ресурсов можно указать только после повторного синтеза и анализа временных ограничений для конкретного устройства и набора настроек.

## 6. Условия аппаратного сравнения

В прежнем верхнем модуле ключ был константой. Синтезатор мог упростить его расписание и связанные операции; такие результаты нельзя автоматически переносить на реализацию со сменяемым ключом. В текущем RTL хранятся 33 подключа и добавлены управляющие регистры. Старые таблицы ресурсов необходимо пересчитать, а не просто перенести в новый отчёт.

Для воспроизводимого сравнения нужно зафиксировать модель ПЛИС, версию Quartus, временные ограничения, размер ключа, состав верхнего модуля, настройки синтеза и то, учитывается ли путь загрузки ключа. Указать отдельно частоту, задержку, интервал выдачи блоков и ресурсы. Названия единиц ресурсов брать из отчёта выбранного семейства ПЛИС.

В прежней курсовой ресурсы MAX 10 обозначены как ALM. Для этого семейства используются логические элементы **LE**, а не ALM; это различие отражено в [документации Intel MAX 10](https://www.intel.com/programmable/technical-pdfs/683105.pdf). В новой таблице следует указать LE и фактические числа из нового отчёта Quartus. Пересчитывать прежние значения ALM в LE с помощью постоянного коэффициента нельзя: необходимо установить, какую величину показывал исходный отчёт, и повторить измерение для исправленного проекта.

Статус на момент этих исправлений: повторный запуск Quartus не выполнен. Новые значения Fmax, площади, энергопотребления и устойчивости к физическим атакам не заявляются.
