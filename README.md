# Serpent: конвейерные реализации на SystemVerilog

В репозитории представлены две реализации шифрования 128-битового блока Serpent с ключом длиной 128, 192 или 256 бит. Обе принимают один блок за такт после загрузки ключа.

| Каталог | Верхний модуль | Раундов в ступени | Задержка принятого блока |
| --- | --- | ---: | ---: |
| `1-s/` | `SerpentEncryptTopPipelined` | 1 | 32 такта |
| `2-s/` | `SerpentEncryptTopPipelined2R` | 2 | 16 тактов |

Размер ключа задаётся параметром `KEY_BITS` при построении модуля: допустимы только `128`, `192`, `256`; по умолчанию — `256`. Значение ключа можно менять во время работы через `key_load`.

## Проверка

Требуются Python 3 и Icarus Verilog: программы `iverilog` и `vvp` должны быть доступны в `PATH`.

Из корня репозитория:

```sh
python3 tests/run_tests.py
```

Автоматическая проверка сравнивает результаты с эталонными значениями и завершает выполнение с ошибкой при несовпадении. Актуальный состав проверок задаётся скриптом в `tests/`; успешный запуск симуляции не является отчётом о синтезе или проверкой временных ограничений ПЛИС.

Набор включает 27 опубликованных NESSIE-векторов, независимый Python-эталон, два теста постоянного нулевого ключа и 24 конфигурации поточной проверки. Подробности — в [tests/README.md](tests/README.md), сохранённый результат проверки исправлений — в [docs/VALIDATION_RU.md](docs/VALIDATION_RU.md).

Исходники имеют расширение `.v`, но используют SystemVerilog, включая массивы портов. Для Icarus необходим флаг `-g2012`. Варианты `1-s/` и `2-s/` следует собирать **по отдельности**: они содержат модули с одинаковыми именами. Файлы из `old/` в текущую сборку не включаются.

В Quartus включайте четыре файла `serpent_*.v` выбранного варианта как `SYSTEMVERILOG_FILE`, а не `VERILOG_FILE`; `tb_serpent.v` предназначен только для симуляции. Это правило описано в [документации Quartus](https://docs.altera.com/r/docs/683475/19.4/intel-quartus-prime-standard-edition-user-guide-getting-started/confine-systemverilog-features-to-systemverilog-files?contentId=jSO_CeUzWzvOE~krRoTujg).

## Интерфейс и протокол

У обоих верхних модулей одинаковые порты:

| Порт | Направление и размер | Назначение |
| --- | --- | --- |
| `clk` | вход, 1 бит | Работа по положительному фронту |
| `rst` | вход, 1 бит | Синхронный сброс, активный уровень — 1 |
| `key_load` | вход, 1 бит | Загрузка расписания ключей и сброс выполняющихся блоков |
| `key_in` | вход, `KEY_BITS` бит | Новый ключ |
| `key_ready` | выход, 1 бит | Ключ загружен и пригоден для шифрования |
| `in_valid` | вход, 1 бит | На `data_in` находится входной блок |
| `in_ready` | выход, 1 бит | Модуль может принять блок |
| `data_in` | вход, 128 бит | Открытый текст |
| `out_valid` | выход, 1 бит | На `data_out` находится результат |
| `data_out` | выход, 128 бит | Шифротекст; при `out_valid = 0` равен нулю |

Порядок работы:

1. Подать `rst = 1` хотя бы на один положительный фронт. Сброс отменяет незавершённые блоки и делает ключ недействительным.
2. Снять сброс, установить `key_in` и подать `key_load = 1` на положительном фронте. Комбинационное расписание разворачивает ключ, а этот фронт сохраняет 33 раундовых ключа. Все незавершённые блоки отменяются; входной блок на том же фронте не принимается.
3. Снять `key_load`. Блок принимается на фронте, для которого `in_valid && in_ready = 1`. Сигнал готовности определяется как `key_ready && !key_load && !rst`.
4. Если блок принят на фронте с номером `n`, `out_valid` и соответствующий шифротекст появляются после фронта `n + 32` для `1-s` или `n + 16` для `2-s`. Между этими фронтами не должно быть сброса или новой загрузки ключа.

Паузы в `in_valid` переносятся в `out_valid` с той же задержкой. Конвейер допускает последовательные принятые блоки каждый такт. Выходного сигнала `out_ready` нет: потребитель должен забирать каждый результат при `out_valid = 1`. Синхронный сброс имеет приоритет над загрузкой ключа. Логическая отмена блоков не означает гарантированного физического стирания всех внутренних регистров.

Интерфейс изменён: прежние экземпляры модулей с одними `clk`, `data_in`, `data_out` необходимо обновить. Все новые входы должны быть подключены; перед первым блоком требуются сброс и загрузка ключа. Минимальный пример подключения варианта `1-s` внутри родительского модуля:

```systemverilog
logic         clk, rst, key_load, in_valid;
logic [255:0] key_in;
logic [127:0] data_in;
wire          key_ready, in_ready, out_valid;
wire  [127:0] data_out;

SerpentEncryptTopPipelined #(.KEY_BITS(256)) dut (
    .clk       (clk),
    .rst       (rst),
    .key_load  (key_load),
    .key_in    (key_in),
    .in_valid  (in_valid),
    .data_in   (data_in),
    .key_ready (key_ready),
    .in_ready  (in_ready),
    .out_valid (out_valid),
    .data_out  (data_out)
);
```

Тактовый сигнал и входные значения задаёт родительский модуль по описанному протоколу. Для варианта `2-s` в примере заменяется имя модуля на `SerpentEncryptTopPipelined2R`; его исходники собираются отдельно.

## Порядок байтов

Первый байт стандартной последовательности байтов занимает младший байт вектора: `data_in[7:0]` или `key_in[7:0]`. Это же правило действует для `data_out`. Каждые четыре последовательных байта образуют 32-битовое слово в порядке little-endian.

Например, последовательность байтов `00 01 02 ... 0e 0f` задаётся в HDL как `128'h0f0e0d0c0b0a09080706050403020100`. В Python:

```python
data = bytes.fromhex("000102030405060708090a0b0c0d0e0f")
hdl_value = int.from_bytes(data, "little")
result_bytes = ciphertext_value.to_bytes(16, "little")
```

При `KEY_BITS = 128` или `192` дополнение до 256 бит выполняется внутри: бит с номером `KEY_BITS` устанавливается в 1, все более старшие биты — в 0. Для 256-битового ключа дополнение отсутствует. Отдельные перестановки IP/FP на интерфейсе bitslice-реализации не требуются.

## Параллельная ECB-обёртка

В каждом варианте есть модуль `SerpentEncryptECB` с параметрами `BLOCKS` (по умолчанию 2) и `KEY_BITS` (по умолчанию 256). Управляющие порты и протокол такие же, как у одиночного ядра; ширина `data_in` и `data_out` равна `BLOCKS * 128`.

Блок с номером `i` занимает срез `[128*i +: 128]`. Все блоки группы принимаются одновременно, используют один ключ и выдаются одновременно. Это аппаратная обёртка для независимой обработки блоков: она не добавляет дополнение сообщений, аутентификацию или защиту повторяющихся блоков, необходимую полноценной системе шифрования сообщений.

## Синтез и исторические материалы

Расписание ключей полностью комбинационное. Путь от `key_in` до регистров подключей требует собственных временных ограничений и проверки в целевой ПЛИС. Однотактный протокол загрузки в симуляции сам по себе не подтверждает достижимость нужной частоты в аппаратуре.

Для исправленной версии повторный синтез и анализ временных ограничений Quartus пока не выполнены. Старые значения частоты и ресурсов нельзя считать результатами этой версии. Хранение подключей и логика `valid`/сброса изменяют аппаратные затраты. Защита от побочных каналов и внесения сбоев в этой реализации не заявляется.

`Serpent.pdf`, прежние схемы и каталог `old/` сохранены как исторические материалы. Они не описывают полностью текущий интерфейс и могут содержать прежние ошибки. Разбор исправлений и формулы для обновления курсовой приведены в [docs/CORRECTIONS_RU.md](docs/CORRECTIONS_RU.md).
